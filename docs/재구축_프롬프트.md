## 2. 절대 보존 규칙 (`DO_NOT_BREAK`) — 재구축 중 반드시 지킬 것

아래 7가지는 `docs/10_AI_HANDOFF.md`에 명시된 항목이다. 재구축/리팩터링 과정에서 절대
깨뜨리면 안 된다.

```text
1. app/core.py의 process_zips() 안 `if groups:` 가드를 유지할 것
   — 없으면 zip이 아닌 파일(PDF 등)을 넣었을 때 바탕화면에 빈 결과 폴더가 생성되는
     버그가 재발한다. (실제 발생했던 버그, docs/05_오류_및_해결이력.md 참고)

2. app/gui.py의 OrderEditor._confirm()에서 2단계 임시이름 리네임(임시 UUID 이름 경유 후
   최종 "순번_원본명"으로 변경) 구조를 유지할 것
   — 한 번에 바로 최종 이름으로 바꾸면 순서가 꼬일 때 파일명 충돌이 날 수 있다.

3. 원본 zip 삭제에는 반드시 send2trash()를 사용할 것
   — os.remove()/shutil.rmtree()로 바꾸면 복구 불가능한 완전삭제가 된다.

4. app/core.py의 PhotoItem을 @dataclass(eq=False)로 유지할 것
   — eq=True로 바꾸면 GUI의 set() 기반 선택 로직이 TypeError(unhashable type)로 깨진다.

5. installer.iss의 AppId({8F1E9C2E-7B3A-4C5D-9E1F-2A6B8C4D7E10})를 절대 변경하지 말 것
   — 바꾸면 기존 설치본 위에 업데이트되지 않고 별도 프로그램으로 인식된다.

6. installer.iss [Registry] 섹션이 HKCR\.zip(zip 기본 연결 프로그램) 자체는 건드리지
   않는 구조를 유지할 것 — 우클릭 메뉴에 PhotoDedup 항목만 추가하고(옵트인),
   사용자의 기존 zip 프로그램 기본 연결(더블클릭 실행)은 절대 변경하지 않는다.

7. "최종 결과폴더로 보내기" 확정 단계는 사람이 직접 눌러야 하는 구조를 유지할 것
   — 자동 실행 모드(zip을 인자로 실행)에서도 이 확정 단계만큼은 자동화하지 않는 것이
     이 프로젝트의 핵심 설계 원칙이다.
```

추가로 재구축 중 지켜야 할 것:

```text
8. app/gui.py의 다운로드 폴더 기본경로는 Path.home() / "Downloads" 형태를 유지할 것
   — 과거 특정 PC 사용자명이 하드코딩되어 있던 것을 GitHub 공개 전 일반화했다.
     절대 다시 절대경로/특정 계정명을 하드코딩하지 말 것.

9. 소스코드/커밋 메시지/문서에 API 키, 비밀번호, 특정 인물의 실제 업무 데이터
   (예: 실제 견적서 내용, 차량번호, 사건번호 등)를 포함하지 말 것.
```

## 4. 실제 핵심 기능 (재구현 시 빠뜨리면 안 되는 것)

`docs/11_SKILL_역분석_MASTER.md`에 근거한 실제 동작이다. "이럴 것이다"가 아니라 코드에
그렇게 구현되어 있는 내용만 적었다.

```text
1. 입력: zip 파일 1개 이상 (드래그&드롭 / 파일선택 / CLI 인자 / "프로그램으로 열기" 우클릭)
2. zip 내부 이미지 추출 → 각 사진의 pHash(perceptual hash) 계산
   - SHA-256도 계산은 하지만 실제 중복 판정에는 쓰이지 않는다(죽은 코드, 알고 있는 상태 유지)
3. 중복 판정: BK-tree로 근사 탐색 + Union-Find로 그룹화
   - 해밍거리(threshold, 기본 5, GUI 슬라이더로 0~20 조절) 이하면 같은 그룹
   - 회전/반전 옵션(기본 켜짐) 켜면 90/180/270도 회전본 + 좌우반전본의 pHash도 함께 비교
4. 대표 사진 선정: 각 그룹에서 zip 내부 등장 순서(order_index)가 가장 빠른 것 1장만
   - 해상도/파일크기/촬영일 등은 전혀 기준으로 쓰이지 않는다
5. 처리 가능한 사진이 0장이면 결과 폴더 자체를 생성하지 않는다 (`if groups:` 가드)
6. 대표 사진만 바탕화면 결과 폴더로 복사(1차 처리는 복사만, 삭제 없음)
7. OrderEditor(순서 편집 창)에서 사람이 직접 순서 재배치/삭제 표시/Ctrl+Z(최대 50단계) 가능
8. "최종 결과폴더로 보내기" 확정 시에만:
   - 2단계 안전 리네임으로 "순번_원본명"으로 최종 파일명 부여
   - 삭제 표시된 사진 실제 unlink()
   - 원본 zip을 send2trash()로 휴지통 이동(완전삭제 아님)
   - 결과 폴더를 FastStone(설치돼 있으면) 또는 탐색기로 오픈
9. GUI 없이도 CLI로 동작 (app/cli.py, argparse 기반)
10. 로그 파일을 디스크에 남기지 않음 (화면 로그창 + 콘솔 출력만)
```

### 6-1. 환경 준비

```powershell
Set-Location "C:\Users\MYCOM\Desktop\Kim's programe\PhotoDedup"
python -m venv venv
```

### 6-2. 소스가 없는 경우 (완전 소실 시)

```bash

```

또는 저장소 접근이 불가능하면 `REPRODUCTION_GUIDE.md`에 포함된 전체 소스 원문을 그대로
파일로 복원한다. 이 경우 복원 후 반드시 아래 7번 "검증"을 전부 실행해서 원본과 동일하게
동작하는지 확인할 것.

### 6-3. 실행 확인

```powershell
python main.py                                        # GUI 실행
python main.py photos.zip --threshold 8 --rotate-flip  # CLI 실행
```

### 6-4. exe / 설치 프로그램 빌드

```powershell
build.bat
```

`build.bat`는 내부적으로 PyInstaller(onefile, --windowed)로 exe를 만들고, 이어서
Inno Setup(`ISCC.exe installer.iss`)으로 설치 프로그램을 생성한다. Inno Setup이
설치되어 있지 않으면 먼저 설치할 것 (`ISCC.exe`가 PATH에 있어야 함).

**주의(Git Bash 사용 시)**: 설치 프로그램을 자동/무인 설치 테스트할 때 `/VERYSILENT`를
쓰면 MSYS가 이를 유닉스 경로로 오인해 인자가 깨진다. 반드시 Inno Setup이 지원하는
`//VERYSILENT`(슬래시 두 개)를 사용할 것. PowerShell에서는 이 문제가 없다.

## 7. 기능별 검증 절차 (빌드/수정 후 반드시 실행)

각 항목을 실제로 실행해서 확인하고, 결과를 PASS/PARTIAL/FAIL/CONFIRM_REQUIRED로
기록할 것. 실행해보지 않고 "될 것이다"라고 적지 말 것.

### 7-1. 중복 판정 로직 회귀 테스트

`REPRODUCTION_GUIDE.md` 내 테스트 zip 생성 스크립트로 다음 조합을 만들어 테스트한다:

```text
완전동일 2장 + 재압축(품질 변경) 1장 + 고유 2장 + 비이미지 1개 + 손상이미지 1개
→ 기대 결과: 전체 6 / 고유 3 / 제거 2 / 읽기실패 1
```

이 숫자가 정확히 나오는지 확인. 하나라도 다르면 `cluster_photos()`/`build_groups()`
로직이 변경된 것이므로 원인을 코드에서 직접 확인할 것.

### 7-2. zip이 아닌 파일 처리 (버그 재발 방지 확인)

```text
- PDF 등 zip이 아닌 파일을 프로그램에 넣는다
- 바탕화면에 아무 결과 폴더도 생성되지 않아야 한다 (DO_NOT_BREAK #1 확인)
```

### 7-3. GUI 순서 편집 → 확정 흐름

```text
- 처리 결과 화면 → OrderEditor 오픈
- 사진 드래그로 순서 변경, 1장 Delete 표시, Ctrl+Z로 복원
- "최종 결과폴더로 보내기" 클릭 → 확인 팝업 → 확정
- 확정 후: 파일명이 "순번_원본명"으로 부여됐는지, 삭제 표시한 사진이 실제로 없는지,
  원본 zip이 휴지통으로 이동했는지(완전삭제 아님) 확인
```

### 7-4. 우클릭 "프로그램으로 열기" 자동 실행

```powershell
# 실제 우클릭 실행과 동일한 방식으로 재현
Start-Process "<설치경로>\PhotoDedup.exe" -ArgumentList '"<테스트zip경로>"'
```

GUI가 뜨고 자동으로 처리가 시작되지만, 확정 단계는 사람이 눌러야 진행되는지 확인
(DO_NOT_BREAK #7).

### 7-5. 설치/제거 테스트 (격리된 상태에서)

```powershell
# 설치 (무인, 로그 남김)
& "installer_output\PhotoDedup_Setup_1.0.0.exe" //VERYSILENT //LOG="install_test.log"

# 레지스트리/바로가기로 실제 설치 여부 확인
Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\*" |
  Where-Object { $_.DisplayName -like "*PhotoDedup*" }

# 제거
& "<설치경로>\unins000.exe" //VERYSILENT

# 제거 후 레지스트리/바로가기가 남아있지 않은지 재확인
```

**주의**: 이 테스트는 실제로 프로그램을 설치/제거하는 동작이다. 반드시 제거까지 완료하고,
레지스트리/바탕화면/시작메뉴에 잔여물이 없는지 확인한 뒤 다음 단계로 넘어갈 것. 설치
테스트 도중 실수로 전체 설치를 남겨두지 말 것.

### 7-6. 설치 파일 해시 기록

배포용 설치 파일을 새로 만들었다면 해시를 기록해서 이후 "같은 파일인지" 검증할 수 있게 할 것.

```powershell
Get-FileHash -Algorithm SHA256 "installer_output\PhotoDedup_Setup_1.0.0.exe"
```

```text
   venv/, build/, dist/, installer_output/, 결과_유니크사진_*/ 등)가 실수로 add되지
   않았는지 git status로 재확인한다.
4. 절대 git force-push를 하지 않는다. 절대 기존 커밋 히스토리를 재작성(rebase -i,
   amend of pushed commit)하지 않는다.
5. installer_output/ 안의 기존 설치 파일을 덮어써야 하면 먼저 사용자에게 확인받는다.
6. Release를 새로 만들 때는 버전 태그(installer.iss의 MyAppVersion과 일치)를 확인하고,
   Asset으로 새 설치 파일과 해시(7-6에서 기록한 값)를 함께 안내한다.
7. 위 모든 점검 결과와 실제 커밋될 diff를 사용자에게 먼저 보여주고, 명시적 승인을
   받은 뒤에만 git push / gh release create를 실행한다.
```
